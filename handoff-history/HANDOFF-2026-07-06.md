## 🎯 Goal

A Python/customtkinter desktop app that runs a full Seventh-day Adventist church
service from one control panel, projecting to a second screen (hymns, Bible
verses, lesson questions, timers, prayer requests, media, images, offering
slide...). The app is mature and in daily real use by the user — most work at
this point is refinement, bug fixes, and adding customization on top of an
already-working feature set, not new architecture from scratch.

  padding" and "full photographic slide" rendering.
- **Lezione themed graphic** (new this session, the big feature): in
  Impostazioni → Lezione → "Grafica lezione", the user loads a template image
  (swapped by hand once per trimestre) and positions 4 draggable/resizable
  boxes (header/date/photo/question) over a live preview
  (`ui/app.py:_lesson_graphic_editor`). At projection time
  (`ui/app.py:_project_lesson_domanda` → `ui/projection.py:show_lesson_graphic`)
  the app composites: the template (fit to screen, no crop), the day's photo
  (assigned once per day via a picker in the Scaletta's Lezione panel, shared
  by all of that day's questions, cropped to fill its own box since it's a
  decorative frame slot), the header text ("2. LA MISSIONE DI GESÙ" — day
  position in the week + day title), the date badge ("Lun, 6 Lug" — computed
  from `data_sabato` + day position, **not** from the "giorno" name string,
  see Gotchas), and the question with its "a."/"b."/"c." letter drawn in the
  header/accent color while the rest of the question stays in the question
  color (`_draw_text_in_box`'s new `lead_text`/`lead_color` params). Falls

  configured — fully backward compatible.

## ❌ Failed Attempts (this session)

### Headless test harness gave a false-positive "background thread callback is broken" alarm
- **What:** Testing the new Bible-import background-thread flow, I drove a
  scratch `App()` with `app.update()` called in a manual polling loop
  (instead of a real `mainloop()`) to check whether `self.after(0, fn)`
  scheduled from a worker thread ever fires.
- **Why it looked broken:** After 40 iterations of `app.update()` +
  `time.sleep(0.05)` (2 seconds), the callback still hadn't run — looked like
  a serious, previously-undetected bug affecting every existing
  `_safe_after`-based feature (hymn DB loading, YouTube downloads, etc).
- **Actual resolution:** It was purely a test-harness artifact.
  `app.update()` in a loop does not reliably pump the specific queued
  `after(0, ...)` event the same way a real `mainloop()` does. Re-running the
  identical repro with `app.mainloop()` (and a 3s safety-quit) made the
  callback fire immediately and reliably. **Lesson: when testing anything
  that depends on a background thread calling back into Tk, drive the test
  with a real (bounded) `mainloop()`, never a manual `update()` polling
  loop** — the polling loop can produce false negatives that don't reflect
  the real app's behavior.

### `find_canvas()` test helper matched the wrong widget
- **What:** Locating the new Lezione template-editor's `tk.Canvas` in a
  headless test by walking `winfo_children()` and returning the first
  `tk.Canvas` with `width > 100`.
- **Why it failed:** customtkinter wraps *every* `CTkButton`/`CTkLabel` in an
  internal plain `tk.Canvas` (their actual draw surface), several of which
  are `width=140` — these matched before reaching the real 520px-wide editor
  canvas. Fixed by raising the threshold to `> 300` (the editor is always
  520px wide, hardcoded).

### `left_click_drag` (computer-use) sometimes doesn't fire `<B1-Motion>`
- **What:** Testing the live app's box-drag interaction with a 10px drag
  distance.
- **Why it failed:** The settings didn't change — the drag was apparently too
  short/fast for Tk to register an intermediate motion event. A larger
  drag (30px) worked correctly and did persist to settings. If a future
  computer-use verification of drag interactions seems to silently no-op,
  try a bigger distance before assuming the app code is broken.

### `pkill -f "python3 main.py"` didn't match the real running process
- **What:** Restarting the live app after code changes.
- **Why it failed:** The actual process command line (as launched on this
  Mac) is `/Library/Frameworks/Python.framework/.../Python.app/Contents/MacOS/Python
  main.py` — it does **not** contain the literal substring `python3 main.py`,
  so the pkill pattern silently matched nothing, and a second `nohup python3
  main.py &` was started alongside the still-alive original, producing two
  competing instances/windows. Fixed by finding the PID via `ps aux | grep -i
  main.py` and killing it explicitly. **Always verify the process is
  actually gone (`ps aux | grep -i main.py`) after attempting to kill it, and
  before starting a new one**, rather than assuming a `pkill -f` pattern
  matched.

## ✅ Working Solutions (key decisions worth preserving)

- **Primary vs. extra Bible languages** are modeled separately
  (`bible_primary_lang` singular, `bible_extra_langs` a set) specifically
  because the user caught a real bug where changing language only affected
  the *reference*, not the verse *text* — `_selected_langs()` guarantees the
  primary is always included in what gets projected.
- **`day_position`** (1-based index within a lesson's `giorni` list) is used
  instead of the `giorno` name string for both date math and the per-day
  photo key, because real Lezionario JSON files have been observed to
  mislabel/duplicate a day name (e.g. two days both called "Mercoledì" in the
  same lesson in the user's actual Q3 2026 file) — matching by name would
  silently merge two different days' photos.
- **`_fit_contain` for anything that must never crop** (QR/offering photo,
  Immagine slot, and now the Lezione template itself) vs. **`_fit_cover` for
  anything that's meant to fill/crop** (decorative wallpaper backgrounds, the
  day's photo *within* its box on the Lezione template) — these are
  deliberately different helpers for deliberately different use cases; don't
  conflate them again.
- **Lezione graphic boxes are fractions of the template's own pixel size**,
  not the screen — this is why the boxes stay correctly positioned however
  the template ends up scaled/letterboxed on different screen resolutions.
- **The "a."/"b." letter uses the existing `lesson_header_color` setting**
  rather than a new dedicated color key, because in the user's mockup the
  letter, the header title, the date, and the verse reference are all the
  same accent color — only the question body is a different color. (Note:
  Next Steps #1 asks to make this independently configurable anyway, since
  the user now wants full control over *every* text element separately.)

## ⚠️ Gotchas / Traps

- **Never call `_render_center()` right after `_nav(...)`** — `_nav()` already
  fully rebuilds whatever view it switches to (including calling
  `_render_center()` itself when relevant); calling it again manually on a
  freshly-destroyed widget tree throws `bad window path name`. Only call
  `_render_center()` directly when you're already on the Scaletta view and
  want to re-render the currently-selected slot's detail panel (e.g. after
  changing `self._sel_slot` or `self._lesson_browse_idx`).
- **`_render_center()` uses `self._sel_slot` (a `Slot` object), not a
  slot-id string** — set that attribute directly in tests, not something
  named `_active_slot_id` (doesn't exist).
- **Settings box format for Lezione graphic elements is `[x, y, w, h]`
  fractions of the TEMPLATE's own pixel size**, not the screen — don't
  confuse this with `verse_text_box`/`verse_ref_box` (Bibbia), which *are*
  screen-fraction boxes. Converting between the two requires the
  `to_screen()` closure inside `ui/projection.py`'s `_redraw()` "lesson" mode
  branch.
- **Always restart the live app process to test code changes** — Python
  doesn't hot-reload. Verify the old process is actually dead
  (`ps aux | grep -i main.py`) before starting a new one, per the Failed
  Attempts note above about `pkill -f "python3 main.py"` not matching.
- **`config/settings.json` is the user's real, live data.** Every test in
  this session used a scratch copy (`core.settings.SETTINGS_PATH` monkey-patched
  *before* `import ui.app`) — keep doing this, and always MD5-diff or
  otherwise verify the real file is untouched by any exploratory/headless
  testing. When testing *interactively* via computer-use against the real
  running app (unavoidable for final visual verification), remember to clean
  up any test template/photo paths and setting overrides afterward.
