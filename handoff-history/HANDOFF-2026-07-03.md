## ❌ Failed Attempts / Hard-won Knowledge

### CTkButton/CTkLabel silently grow past an explicit width/height when `corner_radius` is large
This was **the** recurring bug this session, hit twice (nav rail, then prayer avatars) before the
pattern was understood:
- `CTkButton(width=40, height=40, corner_radius=20, image=<18px icon>)` actually renders at **62×40**,
  not 40×40. `CTkButton`'s internal 5×5 grid layout reserves a minimum padding of `corner_radius` on
  each side (`scaled_minsize_columns = max(corner_radius, border_width+1, border_spacing)`) — with
  `corner_radius = width/2` (needed for a true circle), that padding alone already equals the full
  requested width, before any content is placed, so the widget has no choice but to grow.
- `CTkLabel(width=34, height=34, corner_radius=17, text="MR")` has the same problem (measured: renders
  at 54×34).
- `compound="center"` does NOT fix this — it makes the width correct but the image/text silently
  **stops rendering entirely** (that compound value isn't handled by `CTkButton`'s internal
  positioning logic — only `left/right/top/bottom` are, confirmed by reading `ctk_button.py`).
- **The fix**: a plain `CTkFrame` has none of this image/text-driven sizing logic, so it stays exactly
  the requested size. The shared `_circle()` helper (module-level function, `ui/app.py` ~line 132)
  wraps this: a fixed-size `CTkFrame` + a purely decorative `CTkLabel` placed on top via
  `.place(relx=0.5, rely=0.5, anchor="center")`, with manual `<Button-1>`/`<Enter>`/`<Leave>` bindings
  for click/hover. **Always use `_circle()` for any small round button with text/icon content** —
  never `CTkButton`/`CTkLabel` with `width≈height` and `corner_radius≈width/2`.
- Consequence: `_circle()` returns a `CTkFrame`, not a `CTkButton` — it has no `.configure(text=...)`.
  Where a button's glyph needs to change dynamically (e.g. play/pause toggle), the label is reachable
  as `frame.lbl` — update via `frame.lbl.configure(text=...)`. Three places in this codebase do this
  (`AudioPlayerWidget`/`VideoPlayerWidget`/`PauseMusicWidget`'s `_play_btn.lbl`).
- **Diagnosis method that actually worked**: don't trust zoomed screenshots (crop boundaries create
  optical illusions that look like "cut off" edges even when the shape is fine). Instead, instantiate
  the widget headlessly and check `widget.winfo_width()`/`winfo_height()` against what was requested.

### `CTkSegmentedButton` and `CTkOptionMenu` both reject `fg_color`/`unselected_color`/`button_color="transparent"`
`ValueError: transparency is not allowed for this attribute`. Both widgets need a real color (usually
`CARD_ROW`) even where the design calls for "blends into the background" — this bit twice this session
(once for tabs, once for the Innario database-chip `CTkOptionMenu`, which crashed navigation every
time and **wasn't caught by headless tests** because the test config had no databases configured —
the test now injects a fake database directory specifically to exercise that code path).

### `_open_modal`'s scrim covered the whole window, hiding the nav rail behind every modal
Tk/CTk has no real alpha compositing between sibling widgets — a "transparent" `CTkFrame` still paints
a solid rect (matching whatever `bg_color` it resolves to). Fixed by reparenting the scrim to
`self._content` instead of `self` — nav rail and the (removed) topbar area stay visible; the center
content is still covered (a true dissolve would need an OS-level screen-grab, deliberately not built
just to avoid a permissions prompt for opening "Aggiungi elemento").

### Computer-use screenshot capture is flaky in this sandbox, and stray `python3 main.py` processes survive `pkill`
Both recurring problems from prior sessions, confirmed again: (1) `mcp__computer-use__screenshot`
intermittently fails with `SCContentFilter failure` / returns `nil`, unrelated to any code change —
retry 2-3 times then fall back to headless verification and say so explicitly; (2) `pkill -f
"python3 main.py"` regularly leaves a previous instance running (visible via `ps aux`), which then
shows STALE (pre-edit) behavior in the next screenshot and is confusing — always `ps aux | grep
main.py` after `pkill` and `kill -9` any survivor before trusting a screenshot. Also: the Mac's own
lock screen appeared twice near the end of this session (real OS lock, not a sandbox bug) — don't
attempt to interact with a lock screen, just fall back to headless verification and tell the user.

## ✅ Working Solutions (keep using these)

- **`_circle(parent, text, size, corner_radius, fg_color, text_color, font=, command=, hover_color=,
  width=, height=)`** — module-level function, ~line 132 of `ui/app.py`. The fix for the bug above.
  `size` for a square/circle, `width`+`height` for a pill (e.g. chapter-number chips). Returns the
  frame; `.lbl` is the inner label for dynamic text updates.
- **`App._cat_badge(frame, key, title)`** — small uppercase category label (colored via
  `SLOT_COLORS[key]`) + big title, the header pattern now used at the top of every single slot detail
  view and reused for Lezione/Testo libero. Use this for any new detail view instead of a bespoke
  header.
- **`theme._blend(fg_hex, bg_hex, alpha)`** — flattens a color at a given opacity over a background
  into one solid hex (Tk can't do real alpha). Already used for `SEL_BG` and the prayer avatar
  backgrounds. **Reuse this for Next Step A** (muted book-group colors — blend a hue over `CARD_ROW`
  at low alpha instead of inventing new saturated hex values by hand).
- **Everything from the morning handoff's Working Solutions still applies**: backward-compatible
  constant renaming, the icon canvas/toDataURL pipeline, `theme.icon(name, variant, size)`'s two-file
  light/dark scheme for `variant="muted"`.
- **Headless test pattern, refined this session**: instantiate `App()` on a scratch settings path
  (`core.settings.SETTINGS_PATH` monkey-patched **before** `import ui.app`), MD5-check the real
  `config/settings.json` before/after every run. When testing a screen that depends on real user data
  (Bibbia, Lezione), **point the scratch settings at the user's real, read-only data files**
  (`config/settings.json`'s `lesson_file`, `bibles/*.db`) rather than fabricating fake data — this is
  what caught the `CTkOptionMenu` crash that empty-database tests missed.

8. **[Preghiere] Let the operator choose which names to project, not just "all" or "one at a time".**

9. **[Preghiere] Customizable color per prayer topic/reason.** The "motivo" (e.g. "Salute",

   Spirituale→yellow) instead of the current flat `TEXT_TERTIARY`. Reasons are free-text, not a fixed

10. **[Pausa] Audio fade sequencing at the end of a break, with configurable volumes.** The most
    involved item on this list — currently `TimerWidget._check_warn()` just calls
    `self._app._audio.play_warning(snd)` on top of whatever pause music is already playing, at
    whatever volume. The user wants a proper sequence:
    1. A few seconds before the timer ends, **fade out** the pause-music volume gradually (not an
       abrupt cut).
    2. Once faded, **fully stop** the pause music — it must **not** resume afterward.
    3. Play the warning/announcement audio at a **louder**, separately-configured volume.
    4. Both the pause-music default volume and the warning-audio volume should be settings, editable
       in Impostazioni (natural home: the existing Pausa tab for music volume, Timer or Campanello
       tab for warning volume — user didn't specify exactly where).
    Needs: (a) new settings keys (e.g. `pause_music_volume`, `timer_warning_volume`, both 0-100), (b)
    volume-slider UI in the relevant Impostazioni tab(s), (c) fade+stop logic in `core/audio.py` —
    check what `PlaylistChannel` (~line 205) and pygame's mixer channel API already support
    (`Channel.fadeout(ms)` exists in pygame and is probably the right primitive) before building
    anything custom, (d) wire the sequence into `TimerWidget._check_warn`/`_tick` in place of the
    current bare `play_warning()` call.
